## B1. One shared bounded runner (reuse of `Calls.run`)

**Status.** Design, POSIX prototype `processes.py` in `SCR/prototype.diff`.

**Reproduction of the gap in `Calls.run`.** `RUN SCR/repro/descendant.py`
(`TRAZO_MCP_TIMEOUT=10`): a `docx` command that exits 0 at once but leaves a
child holding stdout; the MCP `build` answers only at the deadline with
"timed out after 10 s" (in production after 1200 s) although the build
succeeded. `SCR/repro/descendant.log`.

**Recommended solution.** Move the mechanism of `Calls.run` (group start,
deadline, group kill, bounded drain, UTF-8 with replacement, output kept on
timeout) into `processes.run(argv, *, timeout, cwd, env, input, linger=5,
started=None, capture=True, on_line=None)`; `Calls.run` keeps its contract
(registry for cancellation through `started`, `TRAZO_MCP_TIMEOUT`,
`ToolError` text) and calls it. Additions over today:
- `linger`: once the leader exits, descendants get 5 s to close the pipes;
  then the group is killed and one more second is given; a pipe still held (a
  detached session) ends the wait with a `Held` result and what was read.
- `Timeout` subclasses `subprocess.TimeoutExpired`, so existing
  `except TimeoutExpired` handlers keep working; `str()` names the command
  and bound.
- Any `BaseException` (Ctrl+C included) kills the group before re-raising, so
  moving children into their own group does not lose terminal Ctrl+C. For
  inherited-stdio steps, use SIGTERM then SIGKILL after 5 s so scripts can
  clean up.
- `capture=False` (steps) and `on_line` (CommandJob log tail) reuse the same
  deadline and group handling.
Prototype tests `SCR/tests/test_processes.py`, 5 OK on macOS: hung command
and its child stopped at 2 s with partial output; same-group holder returns
exit 0 within 5 s and the holder is killed; detached holder ends the wait
within 5 s (`Held`); 3 M characters round-trip through stdin/stdout;
undecodable output replaced. Before the fix the module does not exist; the
baseline behavior the tests forbid is shown by `run_timeout_baseline.py`.

**Rejected.** Calling `Calls.run` itself from non-MCP code (it is
`trazo`-argv-only and raises `ToolError`). Keeping `subprocess.run(timeout=)`
(leader-only kill, Windows unbounded drain). A thread per call with
`communicate()` (cannot stop a blocked drain on POSIX either).

**Invariants.** Every call returns or raises within `timeout + linger + 6 s`
on POSIX; after return nothing of the owned group survives; a successful
command whose descendant holds a pipe is not reported as a timeout.

**Portability.** POSIX: `start_new_session` + `killpg`, same on Linux (CI
covers Linux and macOS). Windows: see B5; the prototype has no Windows path.

**Contract change and justification.** MCP: a held pipe now yields the real
result after 5 s instead of a 20-minute timeout error (reproduced defect).
No change to the deadline, variable or error text otherwise.

**PR.** PR-4 `refactor: share the MCP command deadline with every caller`
(`processes.py` new, `mcp_calls.py`). Tier **high** (`S/mcp*.py`).
Verification: `test_mcp_lifetime.py` (13 tests) unchanged and passing, plus
the new tests; `make typecheck` for strict modules.

**Not verified.** Windows; Linux; the full suite; acceptance; performance
(the select loop returns on EOF, so no added latency is expected; measure
serially with `run.py` before merging).

## B2. Standalone CLI build (`build_graph.py`, `pandoc_run.py`, `frontmatter.py`, `uv_sync.py`)

**Status.** Still open, reproduced.

**Reproduction.** `uv run --project SCR/wt/packages/trazo python SCR/repro/cli_hang.py SCR <mode> 15`
on a copy of the generated example paper (`SCR/papers/example`), `trazo build --force`:
- `pandoc-docx` (Pandoc stand-in `SCR/tools/hang_pandoc.py` hangs on the
  `.docx` call): still running after 15 s, last line `[build] docx: manuscript`.
- `pandoc-meta` (hangs on the metadata template read): still running, and the
  last line (`Generated figures/...`) does not name the hung call.
- `uv` (fake `uv sync` that sleeps, lock changed): still running after
  `[build] python: uv sync --locked`.
In all three a second build with `TRAZO_BUILD_LOCK_WAIT=2` exits 75 (BUSY):
the hung build holds the lock, so the preview Word export, table saves and a
default CLI build wait behind it. SIGINT to the group (terminal Ctrl+C) ended
each one with exit 130. Logs `SCR/repro/cli-*.log`.

**Root cause (high).** No deadline on trazo's own tool calls; nothing names
the stage that is waiting.

**Recommended solution.** Through `processes.run`: Word build Pandoc and
preview page Pandoc `TRAZO_PANDOC_TIMEOUT` (default 600 s, one deadline per
document across both crossref stages, as `pandoc_run.remaining()` already
does); metadata and field text 60 s; `--version` 30 s; `uv sync`
`TRAZO_UV_TIMEOUT` 1800 s. Steps and `[commands]` keep no default (user
analyses can take hours) but run in their own group and are stopped on
Ctrl+C and by outer deadlines. Errors: `BuildError("Pandoc did not finish
the Word file of manuscript within 600 s and was stopped; set
TRAZO_PANDOC_TIMEOUT for a longer build")`, `MetadataError(...)`, `uv sync did not
finish within 1800 s ...`; the existing `guarded` cleanup keeps the previous
DOCX.

Deadline rationale: measured Word builds are 0.4-0.84 s p95 (11,000-word load
paper); 600 s is several hundred times that and below MCP's 1200 s, so the
specific message wins inside MCP. A very large thesis is not measured; the
variable covers it. 1800 s for uv covers a first sync of multi-GB wheels on a
slow link; inside MCP the existing 1200 s still applies (pre-existing limit).

**Rejected.** Reusing `TRAZO_MCP_TIMEOUT` for the CLI (different waiter). A
deadline on user steps by default (kills legitimate long analyses).

**Invariants.** A CLI build with a hung Pandoc, metadata read or uv exits
non-zero within its bound, names the stage, leaves no descendant, releases
the lock and keeps the old DOCX.

**Test that fails before the fix (sketch).**
```python
def test_a_hung_pandoc_stops_the_build_with_a_named_error(self):
    root = copy_of_fixture(pandoc=[sys.executable, HANG_PANDOC, real, "docx"])
    before = (root / "output/manuscript.docx").read_bytes()
    t = time.monotonic()
    result = subprocess.run(trazo("build", "--force"), cwd=root, capture_output=True, text=True,
                            env={**os.environ, "TRAZO_ROOT": str(root), "TRAZO_PANDOC_TIMEOUT": "2"}, timeout=60)
    self.assertLess(time.monotonic() - t, 15)
    self.assertEqual(result.returncode, 1)
    self.assertIn("did not finish", result.stderr)
    self.assertEqual((root / "output/manuscript.docx").read_bytes(), before)
    self.assertFalse(stand_in_processes(root))
```
Same shape for `meta` (expects `cannot read metadata`) and a fake `uv` with
`TRAZO_UV_TIMEOUT=2`. On b775566 the outer `timeout=60` fires (shown above
with 15 s).

**Portability.** POSIX verified only on macOS. Windows: taskkill tree, see B5.

**PR.** PR-5 `fix: bound Pandoc, metadata reads and uv sync in builds`,
`build_graph.py`, `pandoc_run.py`, `frontmatter.py`, `uv_sync.py`,
`submission_fields.py`; `project.py` docs only if a variable is documented
there. Tier **high** (Word build list). Needs `make test-update` only if
template docs change.

**Not verified.** Real Pandoc hangs (simulated by a stand-in); uv's own lock
behavior; Windows.

## B3. Preview watcher: tables command, page Pandoc, build-lock waits, shutdown orphans

**Status.** Still open, reproduced.

**Reproduction.**
- `RUN SCR/repro/watcher.py r3_hung_tables_command`: the tables command hangs
  only in the watcher. Status stays `Build OK`, `synced` stops, a prose edit is
  not shown; MCP `build` waits on the lock until its deadline (8 s here) with
  `[build] waiting for another build of this project`; a CLI build is still
  waiting after 6 s. Only killing the command by hand resumes the watcher.
- `descendant.py`: a tables command that exits at once but leaves a child on
  stderr blocks the watcher for the child's lifetime (21.3 s for a 20 s child).
- `preview_pandoc_hang.py`: a hung Pandoc (metadata read in the page build)
  leaves the page on "building..." with `synced: 0` indefinitely, and the hung
  process survives the preview's shutdown (orphan, PPID 1).
- R1 (A1) is a third failure mode of line 48: strict UTF-8 decoding.

**Root cause (high).** Watcher subprocesses have no deadline, no group, strict
decoding; the watcher holds the build lock while the user command runs; build
lock waits in the watcher have no bound; shutdown does not stop the watcher's
children.

**Recommended solution.**
- `regenerate_tables`: `processes.run(command, timeout=PREVIEW_TABLES_TIMEOUT
  (1200 s, the same default as PREVIEW_DOCX_TIMEOUT since it runs the same
  generator), errors replaced)`. On `Timeout`: table error
  `tables: <command> did not finish within 1200 s and was stopped` (PR #35
  channel), keep `tables_pending` (no automatic rerun of a hang; the next
  spec change retries).
- `preview_render.render`: pass `TRAZO_PANDOC_TIMEOUT` to `pandoc_run.run`
  (already supports `timeout`) and turn `TimeoutExpired` into the page error.
- `build_lock(project, log, wait=None)`: an explicit wait argument (the env
  variable is process-global and popped once, unusable from threads). The
  watcher uses `wait=0`: when busy, report once "tables: waiting for another
  build of this project" and retry on the next poll without blocking prose
  rebuilds. `table.render_one` from the HTTP save uses 20 s (the preparation
  path's value); on timeout the save succeeds and the watcher renders the
  table when the lock frees.
- A process registry in `processes` (`started` callback) and
  `processes.stop_all()` in `server.serve`'s `finally`, so no watcher child
  outlives the preview.

**Rejected.** Moving the tables command into a `CommandJob` (frees the
watcher fully, but changes ordering guarantees PR #35 relies on; larger).
A bounded lock wait for the CLI default (terminal users see the waiting line
and have Ctrl+C; once holders are bounded, the CLI wait is bounded
transitively).

**Invariants.** While a tables command runs longer than its bound, the status
reports it within the bound plus one poll; a watcher child never outlives the
server; the watcher never waits on the build lock.

**Test that fails before the fix (sketch).** Extend `test_preview_tables.py`:
hang the tables command after start (flag file, as in `watcher.py`), set
`PREVIEW_TABLES_TIMEOUT=2` in the `Session` env, edit a spec and prose; assert
within 10 s `ok: False` with `did not finish within 2 s`, `synced` advancing,
the command's pid gone, and after removing the flag and editing the spec the
prose edit is visible. Second test: hung page Pandoc with
`TRAZO_PANDOC_TIMEOUT=2`, assert a page error, then `session.close()` and assert
no stand-in process survives. Not run as tests; the scripts above reproduce both failures on b775566.

**Portability.** Group kill as in B1; Windows as B5.

**PR.** PR-6 `fix: bound the preview watcher's commands and lock waits`,
`preview_watch.py`, `preview_render.py`, `build_lock.py`, `server.py`,
`table.py`. Tier **medium** (none in the high list; `build_lock.py` signature
gains a keyword with the old default).

**Not verified.** HTTP table save during a hung build (code reading:
`table_editor.publish`/`table.patch` call `render_one` outside `review_lock`, so
only that request hangs, not every save).

## B4. `CommandJob` (`background.py`, run at line 58, except at line 79)

**Status.** Still open, reproduced. The documented "cleanup wait()" (line 86)
is bounded on POSIX by the SIGKILL timer; the real defects are elsewhere.

**Reproduction.** `descendant.py`, timeout 4 s, grace 5 s:
- same-group child holding stdout after exit 0: `state=error`, exit 0, tail
  `build stopped: timed out after 4 s` (success reported as a timeout);
- detached child: `state=running` after 20.3 s, timeout ignored, until the
  child exits (unbounded in general).

**Root cause (high).** The job waits for stdout EOF, not for the leader;
`kill_group` cannot reach a detached session.

**Recommended solution.** Run through `processes.run(..., on_line=...,
started=self._register, linger=5)`; `stop()` keeps killing the group through
the registered process; a `Held` result finishes the job with its real exit
code and a log line "a process started by the build kept its output open and
was left running" (detached) or "was stopped" (same group).

**Invariants.** A job leaves `running` within `timeout + grace + linger + 1`
seconds; exit code 0 with a held pipe is `ok`.

**Test sketch.** `test_background.py`: start the two `HOLD` commands from
`SCR/repro/descendant.py`; assert `state == "ok"` within 7 s for the first
and `state != "running"` within 7 s for the second. Both fail on b775566 (shown).

**PR.** PR-7 `fix: finish background jobs when their command exits`,
`background.py`. Tier **medium**.

**Not verified.** Windows.

## B5. Windows: process trees and pipe reader threads

**Status.** Documented limit; code reading only (no Windows machine here).
Correction by the coordinator: `.github/workflows/windows.yml` already runs the
package tests on windows-2025, so the new runner tests run there unchanged.

**Facts from code.** `group_options()` uses `CREATE_NEW_PROCESS_GROUP`;
`kill_group` runs `taskkill /F /T` (30 s bound), which follows parent links at
that moment and misses descendants whose parent already exited. CPython's
Windows `communicate` uses daemon reader threads; after a timeout
`subprocess.run` calls `communicate()` with no timeout (unbounded when a
grandchild holds the pipe). `Calls.run` avoids that (5 s, streams not closed,
reader threads left blocked until the holder exits: a thread and handle leak
per occurrence in the long-lived MCP server, not a hang).

**Recommendation.** The runner's Windows path: own reader threads into lists
it can read at any time, `process.wait(timeout)` for the leader, linger, then
taskkill, then return `Held` without closing handles the threads own. Full
containment needs Job objects (ctypes `CreateJobObjectW`,
`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, assignment right after start; a child
spawned before assignment escapes). Owner decision: ship the POSIX path with
Windows documented as best effort, or make the Windows path and its tests in
`windows.yml` a condition of PR-4.

**Next experiment.** On a Windows runner: `python -m unittest test_processes`
plus a variant whose detached child uses `DETACHED_PROCESS`. Expected:
hung and same-group cases pass with the threaded path; the detached case
returns `Held` within linger. If the same-group case fails (taskkill misses an
orphan), Job objects become necessary before claiming the invariant on Windows.
